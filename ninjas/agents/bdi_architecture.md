**Related:** `deliberative_architecture.md` (BDI is the best-known deliberative model), `introduction.md`.

## 1. Intuition first

BDI models an agent the way we describe a person making practical decisions:

- **Beliefs:** what I think is true right now. ("It is 8:40, the meeting is at 9, traffic is heavy.")
- **Desires:** what I would like to achieve. ("Be on time, have breakfast, go to the gym.")
- **Intentions:** what I have **committed** to doing. ("Skip the gym, grab breakfast on the way, leave now.")

The key insight: **you can't pursue every desire at once.** A rational agent picks a few desires, commits to them as intentions, and sticks with them until there is a good reason to change. That commitment is what makes behaviour stable and goal-directed instead of jumping around.

Origin:
- Philosophy: Michael Bratman's theory of human practical reasoning (1987).
- AI: formalised by Anand Rao and Michael Georgeff (early 1990s), who also built practical systems.

---

## 2. Components

| Component | What it is | Example (travel assistant agent) |
|-----------|-----------|----------------------------------|
| **Beliefs** | The agent's knowledge of the world, itself and others. Can be wrong or outdated. | "Flight AI-101 is delayed 2 hours", "user prefers aisle seats" |
| **Desires (goals)** | States the agent would like to bring about. Can conflict. | "Get the user to Delhi by 6 pm", "keep cost under Rs 10,000" |
| **Intentions** | Desires the agent has committed to, plus the plan chosen for each. | "Rebook on the 2 pm IndiGo flight" |
| **Plan library** | Pre-written recipes: "to achieve goal G, when context C holds, do steps S1..Sn". | "Rebook flight: search alternatives -> check price -> hold seat -> confirm with user" |
| **Events** | Triggers: new perceptions, new goals, plan failures. | "Delay notification received" |
| **Interpreter (reasoner)** | The loop that updates beliefs, picks intentions and runs plans. | The orchestrator |

## 3. The BDI reasoning cycle

```
loop:
  1. Perceive        -> read events (sensor data, messages, tool results)
  2. Belief revision -> update beliefs with what was perceived
  3. Option generation -> which desires are relevant now?
  4. Deliberation    -> choose which desires to commit to (become intentions)
  5. Means-ends reasoning -> pick a plan from the plan library for each intention
  6. Execute         -> run the next step of the current intention
  7. Reconsider?     -> is the intention achieved, impossible, or no longer wanted? drop or change it
```

### Simple code sketch

```python
while True:
    events = perceive()
    beliefs.update(events)                                   # B

    options = [d for d in desires if d.relevant(beliefs)]    # D
    intentions = deliberate(options, intentions, beliefs)    # I: commit to a few

    for intent in intentions:
        if intent.plan is None:
            intent.plan = plan_library.find(intent.goal, beliefs)  # means-ends
        intent.plan.execute_next_step()

    intentions = [i for i in intentions
                  if not i.achieved(beliefs) and i.still_possible(beliefs)]  # reconsider
```

## 4. Why BDI is practical: the plan library

Classic deliberative planners (like STRIPS) plan **from scratch** by searching every possible action sequence. That is slow.

BDI agents usually pick from a **library of pre-written plans** written by experts. Choosing a recipe is far faster than searching for one. That makes BDI fast enough for real-time systems, and it's why BDI is often described as a **practical, partly hybrid** deliberative architecture.

Trade-off: the agent can only do what its plan library covers. New situations need new plans written by humans (or, today, generated by an LLM).

## 5. Commitment: how stubborn should the agent be?

Rao and Georgeff described commitment strategies:

| Strategy | Keeps an intention until... | Risk |
|----------|---------------------------|------|
| **Blind commitment** | It believes the intention is achieved | Keeps trying the impossible |
| **Single-minded** | Achieved **or** it believes it is impossible | Ignores that the goal may no longer matter |
| **Open-minded** | It is achieved, impossible, **or no longer desired** | Balanced, most commonly preferred |

The core balance:
- **Reconsider too rarely:** the agent keeps working on stale or pointless goals (over-commitment).
- **Reconsider too often:** the agent spends all its time re-deciding and never finishes anything (over-reconsideration).
- The right balance depends on how fast the environment changes.

## 6. Real-world use

- **PRS (Procedural Reasoning System):** the early BDI system (Georgeff and Lansky, 1980s), tested on fault diagnosis for the NASA Space Shuttle's reaction control system.
- **OASIS:** an air traffic management prototype at Sydney airport built on a BDI platform (dMARS).
- **Frameworks:** dMARS, JACK, Jason (AgentSpeak language), Jadex (Java-based).
- **Other domains:** military and flight simulations (realistic pilot behaviour), business process automation, game AI characters, robotics.

## 7. BDI and modern LLM agents

BDI is a very good mental model for designing LLM agents:

| BDI | LLM agent equivalent |
|-----|---------------------|
| Beliefs | Context window + memory (RAG, user profile, tool results) |
| Desires | The user's goals and the system prompt's objectives |
| Intentions | The current plan / to-do list the agent has committed to |
| Plan library | Tools, skills, SOPs, prompt templates, workflows |
| Means-ends reasoning | LLM choosing which tool or skill fits the goal |
| Belief revision | Updating state after each tool result |
| Reconsideration | Re-planning when a step fails or the user changes the request |

Lesson for LLM agents: keep an **explicit intention / plan state** (like a to-do list), and define **when to reconsider** (failure, new info, user change). Without that, LLM agents either drift away from the goal or keep re-planning and never finish.

## 8. Pros and cons

**Pros**
1. Intuitive: it mirrors how people reason, so it is easy to explain to clients.
2. Goal-directed and stable: commitment avoids aimless switching.
3. Fast for a deliberative design, thanks to the plan library.
4. Explainable: you can show beliefs, goals and the chosen plan ("why did you do that?").
5. Handles multiple and competing goals with explicit priorities.

**Cons**
1. Limited to its plan library; no built-in learning.
2. Writing and maintaining plans and beliefs takes expert effort.
3. Tuning reconsideration (when to drop or change intentions) is hard.
4. Wrong beliefs lead to confidently wrong actions.
5. Classic BDI uses symbolic logic, which handles messy, uncertain real-world data poorly (one reason LLMs are now used to fill that gap).

## 9. Full stack analogy

| BDI | What I already use |
|-----|--------------------|
| Beliefs | Application state / Redux store / DB |
| Desires | Product requirements / backlog |
| Intentions | Sprint commitments: what the team picked from the backlog |
| Plan library | Runbooks, playbooks, reusable service methods |
| Reconsideration | Sprint review: drop or re-prioritise items when things change |

---

## 10. FDE angle

In a client design doc, BDI gives a clean way to explain an agent to non-AI stakeholders: "here is what it knows (beliefs), what it is trying to achieve (desires), what it has committed to right now (intentions), and the approved playbooks it is allowed to use (plan library)." The plan library is also a natural **governance boundary**: the client approves the playbooks, and the agent only acts through them.
